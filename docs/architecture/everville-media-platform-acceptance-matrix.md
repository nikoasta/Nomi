# Everville Media Platform RFC Acceptance Matrix

Status: Test-first acceptance contract

Milestone: `evmedia-r20.4`

## Source Boundary

This matrix derives requirements only from:

- Beads issue `evmedia-r20.4`, as returned by `bd show evmedia-r20.4`.
- `docs/product/2026-07-16-everville-media-portal-workflow-draft.md` (`PRODUCT`).
- `.codex/handoff.md` (`HANDOFF`).
- `.codex/project-index.md` (`INDEX`).

No implementation directories were inspected to produce this matrix. The RFC
must validate its current-state claims separately and record the evidence it
used.

## Decision Discipline

This matrix does not approve an architecture. In particular, `Vercel +
Supabase` is a candidate for comparison only. Cloud architecture, the private
delivery target, private remote configuration, CI/CD, direct-publishing scope,
pilot selection, approval ownership, day-one Brand Kits/templates, and
mandatory legal-review classes remain unapproved.

Every RFC decision must have a stable ID, status, owner, date, alternatives,
rationale, and evidence reference. Allowed statuses are `PROPOSED`, `APPROVED`,
`REJECTED`, `DEFERRED`, and `BREAKPOINT`. `APPROVED` is valid only when the RFC
records the explicit owner review that approved it. Missing decisions are not
implicit approval.

Reviewer outcomes:

- `PASS`: required evidence exists, the deterministic check passes, and the
  decision rule is satisfied.
- `BLOCKED`: evidence is complete enough for review, but an explicit owner
  decision or named external dependency is still required.
- `FAIL`: evidence is absent, internally inconsistent, unsupported by the
  allowed sources, or presented as approved without recorded approval.

The RFC may enter the architecture breakpoint only when every row is `PASS` or
`BLOCKED` and every `BLOCKED` row names its owner decision or dependency. The
milestone may be accepted only after the architecture breakpoint is explicitly
approved and all downstream acceptance criteria and dependencies are reconciled
to the approved RFC.

## Milestone Review Record

The reviewer must record the RFC version/commit, review date, architecture
breakpoint result, row outcomes, unresolved owners, and final milestone result.
A completed matrix without an explicit architecture-breakpoint approval is
review-ready evidence, not an approved platform architecture.
